# Native Grok accounts (PM-254)

Settings → Agents → Grok → Accounts uses the same account layout and actions as the other native switchers. It detects the default login, displays its email, saves/imports profiles, supports nicknames and drag reordering, and refreshes all or individual usage reports. Switching requires confirmation. Already running Grok processes retain their login until deliberately restarted; ProjectManager does not restart them automatically.

The credential location follows Grok: `GROK_HOME`, then `GROK_CONFIG_DIR`, then `~/.grok`, with `auth.json` inside. Supported OIDC entries include account-namespaced `<issuer>::<account-id>` keys and use the exact HTTPS origins `auth.x.ai` or `accounts.x.ai`. The original document is preserved so refresh and provider metadata survive a switch. API-key-only logins have no verified account/billing contract and are not offered as saved accounts.

Saved credentials and the previous-login backup are encrypted with AES-256-GCM in `data/grok-accounts/*.enc`. The separate `encryption.key` must be backed up with these files. Registry metadata contains no tokens or cached quota. Encryption protects stored copies; anyone with access to both the key and ciphertext can decrypt them. The live Grok auth file remains in Grok's own format. Removing a saved profile does not sign out the active CLI.

Usage comes directly from Grok's billing service using that profile's bearer credential. The percentage is credits **used**, not credits remaining. Plan metadata is optional. Usage is cached in memory for at most 60 seconds before marked stale and automatically refreshed while the drawer is open. Manual refresh requests fresh provider data. Identity includes issuer, principal and team; cache entries also require an identical credential fingerprint. Failed, expired or malformed responses show unknown usage rather than zero. Reset times come from the provider and use the shared live countdown; reaching a reset never invents a replenished quota. Automatic rotation is opt-in (see below).

Switching saves the current CLI's latest credential before replacement and verifies the write. A concurrent external login aborts the switch. If a write fails, the previous credential is restored. Missing encryption keys fail closed: restore the key and encrypted files together from backup, or remove the damaged saved profile and save a fresh `grok login`. Do not share these files or commit them.

Grok can clear its live `auth.json` to `{}` after a rejected refresh token. Saved encrypted profiles remain visible in Settings with a signed-out explanation. A malformed live file also leaves the list visible, but switching refuses to overwrite it. A saved refresh token may have been revoked; its presence cannot guarantee renewal. Sign in again for that account and save the renewed login. ProjectManager never initiates browser authorization or refreshes saved tokens itself.

## Automatic rotation (PM-412)

The checkbox above the account list, "Automatically switch accounts when credits run out", is off until chosen. When it is on, `server/agents/grokRotation.ts` decides and the supervisor's tick acts:

- **What authorizes a switch.** Only a billing reading of the login in use that is under a minute old, bound to that exact credential, and at 99% or more of its credits. A failed, stale or reset-due reading never does.
- **The CLI's message.** Grok Build draws "You hit your weekly limit." in a box above a "Buy more credits" choice (seen in real session logs); the 1.0.62 binary also has "You hit your free usage limit." and "out of credits or over your spending limit". Seeing one of these only makes the tick read billing every 15 seconds instead of every five minutes. Rate-limit messages ("You've hit the rate limit for your plan", "The service is busy") clear by waiting and are ignored.
- **Per-account choice (PM-531).** While the setting is on, each saved login shows an Auto-switch box, as in the Codex switcher. Unticking it stores `autoSwitchEligible: false` on that login's registry row (kept when the login is re-saved with renewed tokens), and rotation never picks it. Ticking it again removes the flag.
- **Which login next.** Saved logins that are not the current one, readable, unexpired, and below 99% by their last reading, least used first, then registry order (the order they were saved; the panel's drag order is a browser preference the server does not see). An unexpired login whose usage is unknown is tried last. Expired saved logins are skipped even when they contain a refresh token, to avoid authorization loops with revoked tokens. Saved tokens are never refreshed by ProjectManager, since that would retire the saved refresh token.
- **What happens to sessions.** Grok processes keep their login until restarted. Sessions that are idle, or showing the message, restart on the new login and resume their conversation (`--resume <session id>`); the ones that showed the message also get Continue. A session that is working keeps the old login until it is restarted.
- **No ping-pong.** A login it left is skipped until its own credit reset, or for a day when the reading has no reset time. A failed switch sets that candidate aside for 15 minutes. Turning the setting off clears the skip list.
- **Session supervision** (PM-405) already leaves a session showing a limit message to the provider's own continuation, so the two never act on the same blocked session.

`grok-swap` is a useful reference for Grok Build OIDC storage, issuer identity, billing requests and recapturing refreshed tokens. ProjectManager implements these contracts directly with Node's standard library and adds its existing UI/API security model; it does not install or execute the Python tool.

Pinned MIT source and license are retained in [upstream/grok-swap](upstream/grok-swap/REFERENCE.md) for recovery and comparison if Grok changes its private protocol. These endpoints are version-dependent, so unrecognized data fails to unknown usage. Automated tests use temporary credential files and injected HTTP fixtures; they do not change live accounts or contact the provider.
